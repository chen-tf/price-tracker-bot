日期：2026-11-22。正式服務保持 Workers Free、D1 Free，未使用 Browser Run、付費代理或常駐主機。

82 次批次寫入的 Workers tail 均為 outcome=ok，觀察到 CPU 最高 5ms。這是同步寫入請求的 CPU，不能當作整段來源查價的 CPU。另一次原生 Cron 查 20 件時觀察到 14ms，故正式排程降為每批 10 件；手動補查仍每批 100 件來源、20 件同步。網路等待時間也不等於計費 CPU 時間。

## 減少不必要的工作

1. 手動來源查價每 100 件共用價格 API；庫存最多四個並行請求，移除原先每四件固定停一秒。
2. 已由 momo 明確確認下架的商品每日重試。若批次仍回空名稱與 0 元，保留舊紀錄，不逐件查庫存；重新出現有效價格即恢復正常庫存檢查。100 件這類商品可只用 1 次來源請求，舊流程需 101 次。
3. 相同來源編號共用庫存請求。10 件異常商品原來已被 momo 對應到新編號，經商品頁結構化資料驗證後保存 source_id，不需每次解析網頁；原訂閱主鍵與基準價保留。
4. 每 20 件有效價格與通知改由兩句 SQL 在同一 transaction 提交，原先需 40 句；下架或錯誤更新各一句。SQL 減少與計費 rows written 是不同指標，以上額度比例採實際 meta.rows_written。
5. 一般補查只選到期商品，retry-errors 只選實際失敗商品，full-refresh 才重查全部。來源端批次抓取後，每 20 件同步一次，控制 Worker 單次 CPU 與 subrequests。
6. 正式 Cron 每批最多 10 件；有指令或待送通知的分鐘先處理訊息，避免同次疊加查價與發訊 CPU。維護清理每小時一次。

以改造後同一批 1635 件推算：舊方法需 82 次批次價格加 1635 次庫存，共 1717 次來源請求；新方法最多 17 次批次價格加 477 次庫存，共 494 次，少約 71%。相同來源編號去重還可略少，該推算不含異常重試。

## 驗收

- 24 個 Node 測試與 3 個 Python 匯入測試通過，包含 workerd／D1 實際交易、批次效率、下架後回架、來源失敗不覆蓋價格、新舊編號、私人訂閱與個人基準價。
- 10 件異常商品重試約 7 秒完成，D1 讀取 93 筆、寫入 29 筆。
- Telegram /price 即時測試：商品 4811545 回 1111 元；舊編號 10213900 透過來源 14309374 回 7111 元，均顯示可購買。
- 全量結束時 /health 為 failed_products=0、stale_products=0、pending_updates=0、pending_messages=0。
- Fly price-tracker 應用已刪除，Dashboard 確認 0 個應用、0 台機器；原本無 Volume。舊 Supabase 與私人備份保留。
